# /video-studio — one skill for any video

A single entry point that (1) identifies the TYPE of video, (2) applies the
right playbook, and (3) runs the shared, proven production pipeline. Helper
scripts live in `scripts/` (beatmap.mjs, frames.sh, setup.sh).

**Core promise: every video gets an ORIGINAL template — no exceptions for
"just the bones".** Never reuse a previous product's design system, and never
start by copying an old composition file as scaffolding. Research the brand,
then design a new visual world for it — new stage, palette, hero objects,
motion language. (Sequel/reference-clone exceptions below.)

**STUDIO HOME: `~/promo-video-studio` — everything happens there regardless of
the current working directory.** If it doesn't exist, bootstrap it:
`bash <skill-dir>/scripts/setup.sh` (auto-installs ffmpeg/Node, scaffolds the
Remotion studio, copies helper scripts). Manual fallback:
`npx create-video@latest ~/promo-video-studio` (blank, TypeScript), then copy
this skill's `scripts/` in. Always copy the final MP4 to the user's working
directory too.

## Prerequisites & first-run (do once per machine)

Run `bash <skill-dir>/scripts/setup.sh` — it installs ffmpeg + Node 18+ and
scaffolds the studio. Details / manual fallbacks:

- **ffmpeg + Node 18+** — setup.sh auto-installs via the machine's package
  manager (brew / apt / dnf / pacman / choco). If NONE is present (common on a
  bare Windows box), install manually, then re-run setup.sh:
  - Windows: `winget install Gyan.FFmpeg OpenJS.NodeJS` (or `choco install
    ffmpeg nodejs`). Run setup.sh from **Git Bash**, not PowerShell.
  - macOS: `brew install ffmpeg node`. Linux: use apt/dnf/pacman.
  - Verify: `ffmpeg -version` and `node -v` (≥18).
- **Remotion + create-video** — no global install needed; fetched on demand via
  `npx`. First render downloads a headless Chromium (one-time, automatic).
- **ElevenLabs voiceover (OPTIONAL — only if the cut needs narration)** — put the
  key in the studio's `.env` as `ELEVENLABS_API_KEY=...` (gitignored; never echo
  it in chat, never hardcode or commit it — scripts read it from `.env` at
  runtime). Use `scripts/eleven-vo-ts.mjs` so you get word-level timestamps for
  captions. No key → skip VO; music-only cuts need none of this.
  *(HeyGen is legacy — the older `HEYGEN_API_KEY` path still exists but is not
  the default for this user.)*
- **Music** — user-supplied licensed track, or ElevenLabs Music generated by the
  USER from a prompt you write (give genre/BPM/mood, explicit length, and the
  exact drop timestamp to hit the payoff). Never bundle an unlicensed track.
- **Fonts** — compositions default to Inter / JetBrains Mono. Headless Chrome
  falls back to system-ui if they're absent (fine for drafts). For pixel-exact
  type, load them in-comp via `@remotion/google-fonts` (`npm i
  @remotion/google-fonts` in the studio) rather than relying on OS-installed
  fonts.

# Part 1 — Pick the TYPE, then intake

## Step 0 — Identify the type (ask if unclear), then intake

The requester should NOT have to explain their product. Flow:

1. **Get the website URL.** If not provided, ask for it (plus a logo image if
   they have one) and wait. No website → ask for a 2–3 sentence description.
2. **Research before asking.** WebFetch the homepage AND /pricing, /features,
   /products/*. Pull brand hex colors from the site CSS (curl the stylesheet,
   grep for hex codes / brand CSS vars). Extract: what the product truly does,
   exact taglines, feature/module list, pricing, CTA, palette, audience, and
   any REAL published metrics (citable; invented numbers are not). NEVER ask a
   question the site already answers.
3. **Ask ONE batch of questions** (AskUserQuestion, 4 per call, up to 3 calls,
   most-important first; put your research-informed best guess as the
   recommended first option so "all defaults" still yields a great video).
   Every option must be CONCRETE and product-specific (name the actual
   stage/palette/hero-object, quote the actual tagline, propose the actual
   example scenario) — never generic adjectives. Use the `preview` field for
   ASCII scene sketches / sample on-screen copy. Ask about the things that
   cause re-renders: exact end-card copy, the opening scenario verbatim, claim
   aggressiveness, words to avoid. Question bank: **duration; features vs
   outcomes; scene wishlist; audience; hero moment; goal + CTA; real numbers;
   what must NOT be claimed; claim aggressiveness (users often want bolder
   than the site — ask, don't guess conservative); exact end-card wording;
   words to avoid; theme/visual direction (3–4 concrete art directions);
   tone; brand colors/logo; music track.**
   Then add the type-specific questions from the playbook.
4. **ALWAYS ask WHICH CUT(S) to render — never assume, never infer.** Give this
   its own question in the batch, every single time: **full-length 16:9? a 9:16
   short? both?** — plus resolution (4K vs 1080p) and, if both, whether the
   short is a trimmed highlight or its own edit with its own script. This is the
   single most expensive thing to get wrong: each cut is a separate multi-hour
   render, and a short is NOT a reframe of the long one (different scene
   selection, different VO, different pacing, different layout — see the
   portrait rules in Part 3). Do not treat "make a video" as authorizing both,
   and do not silently skip the vertical because it wasn't mentioned.
5. **Ask EVERYTHING before building: no silent defaults.** On top of the
   question bank, always cover: **product reel or VALUE reel** (educational tip
   that stands on its own, with the product at most a soft mention); the **story /
   scenario** in one sentence (whose problem, what constraint, what changes);
   **what real material exists** (screen recordings, hands/desk/phone footage,
   founder takes, photos) vs what must be illustrated; **voice** (the founder's
   own, a cloned voice, AI VO, or silent) and whether the face may appear;
   **caption style**; **music** (a supplied track or a prompt the user generates);
   **references** the user likes and **what to avoid**; format + resolution +
   length. Use as many AskUserQuestion rounds as it takes.
6. **Play back the full brief and WAIT for an explicit go.** (story · audience ·
   type product/value · format · length · look · voice · captions · music · CTA ·
   what we will NOT do). Building before the brief is confirmed is the most
   common cause of a wasted render.

## Type playbooks

All types share the pipeline (Part 3); they differ in visual approach,
narrative structure, length, and format.

- **Promo / Launch** — desire + brand feeling. Hook → problem → solution →
  proof/payoff → CTA. 30–60s, 16:9 (+9:16). Illustrated, music-driven, a
  signature payoff synced to a music drop. (This part uses the full engine
  below most heavily.)
- **Demo / Product walkthrough** — show how it works + the value. Pain → enter
  product → walk the real flow (2–4 steps/features) with callouts → result →
  CTA. 60–120s. **Recreate the real UI and data as clean ORIGINAL illustrated
  UI** (redraw screens/layout/copy) — never paste raw screenshots; use measured
  callout highlights + a simulated cursor for clicks. Intake: which flow, real
  layout/copy, any read-only/permission disclosures to state accurately.
- **Explainer** — make a concept click. Question/problem → the idea → how it
  works (metaphor/diagram animation) → why it matters. 60–90s. Narration-led,
  clarity over flash.
- **Tutorial / How-to** — teach a task. Goal → numbered steps, ONE per beat →
  recap. Length = the task. UI callouts, imperative VO ("click…", "then…"),
  patient pacing.
- **Social / Short** — stop the scroll. **The hook is SPOKEN from frame 0** (voice + motion
  immediately; never a logo intro, music-only or text-only opening): a short, punchy
  pattern-interrupt that promises a payoff ("Wait! Let me save 30 minutes of your day.").
  The viewer decides in ~1 second. No outro/end card; end on the last payoff line.
  If the footage lacks a hook line, generate one in the speaker's cloned voice and
  match it to the footage's sound. → one value → CTA.
  15–35s, 9:16. **Caption everything** (sound-off), but in the crafted style
  from the Craft bar below, not big kinetic-type/karaoke pills. Cut on action
  every 2–3s; faster pacing is OK here.
- **Value reel (educational)** — teach ONE useful, standalone thing the audience
  can use today even if they never buy (a mistake, a rule, a 3-step fix, a
  myth). Hook = the problem in the viewer's words → the insight → a concrete
  example with real numbers/UI → a one-line takeaway. The product appears at
  most as the tool in the example or a quiet end card; no feature list, no hard
  sell. Balance a channel with value reels alongside product reels. A proven
  shape: numbered chapters (mono `// 01 — hook` label + a live counter that turns
  the argument into numbers), a hook that promises a payoff at the end, and a
  comment-keyword CTA ("Comment UTM and I'll send you the template"). See
  LEARNINGS.md.
- **Feature tour / Use-case** — cover several features. Intro → 3–5 vignettes
  (consistent per-vignette template) → payoff → CTA. 45–90s.
- **Testimonial / Case study** — proof via outcome. Claim → proof (real quote +
  result stat) → outcome → CTA. 30–60s. Quote cards, result stats. **Real
  quotes/numbers only.**
- **Ad (conversion)** — one action. Tight, benefit-led, CTA-heavy, single
  offer, 15–30s, often 9:16 + 16:9 pair. Lead with the benefit, not the brand.

## Originality (all types) — the anti-fingerprint checklist

Learned the hard way: a user recognized a "new" video as a re-skin even though
every color/object changed. Structural DNA leaks through five channels — ALL
must differ from previous videos:
1. **Type treatment** — the signature text effect (typewriter+caret, mask
   slide, tracking collapse, inverted pills, serif contrast).
2. **Layout archetype** — vary the grid (corner captions, left-anchored,
   split-screen), not always kicker + rule + centered headline.
3. **Payoff physics** — vary the verb (invert flash, list-reorder slam,
   split-wipe, letterpress stamp, build-from-one-pixel), not always shockwave
   rings + particles.
4. **Scene-wrapper motion** — change the in/out style (zoom-through blur vs
   lateral sway vs vertical roll).
5. **Recurring stage prop** — dust + spotlight vs grain + ghost object.

**The reliable way to be original: derive the world from the product's CORE
INTERACTION, not a generic "premium dark stage."** Search product → typed
queries + result rows; jeweller → a showroom; courier → parcels + routes. When
a draft feels derivative, this is the fix.

**Two exceptions:** (1) an explicit series/sequel cut of the user's OWN product
→ import that video's exported primitives and reuse them verbatim (a theme
change like dark→light is then a RECOLOR pass, not a rewrite). (2)
**Reference-clone mode** — the user gives a reference video and says "make it
exactly like this": DON'T design original; extract frames (ffmpeg), READ them,
map the shot grammar (beat list, type treatment, stage, hero-shot types,
transitions, dark→light shifts, outro), and clone it shot-for-shot adapted to
the brand. "Inspired by" is not what they asked — match the structure literally.
**References are inspiration, never a template.** Unless the user explicitly
says "make it exactly like this", stay open: study many references (not one
brand), extract the underlying principles (why it works), mix them with our own
ideas and the product's own world, and never mirror any single brand's
signature elements (its mascot, UI style, caption placement, colour world,
end card). The test: someone who knows the reference should NOT recognise it in
our video. Say which principles you took, and from where, when proposing an
approach.

## Craft bar — not "AI-ish" (read before designing)

Feedback that reset the bar: technically good videos still read as
"AI-generated" when they lean on generic motion-graphics tropes. The fix is
craft and realism, not more effects. Rules:

- **Story before product.** A specific person, a small real task, a concrete
  constraint ("portal only accepts < 2 MB"), **failure before success**, and
  real numbers ("3.05 MB → 1.52 MB"). Feelings are allowed ("it feels
  overwhelming").
- **Real texture over flat vector.** Prefer real footage (a skyline or room
  timelapse, POV hands on keyboard/trackpad, a desk, a phone in hand) as the
  world, with the product UI placed INTO it. Film the screen like a physical
  object: warm film grade, lifted blacks, soft vignette, light grain/bloom,
  gentle handheld drift, macro crops (show one UI element at 200–400%).
  Illustrated-only worlds (dot grids, blobs, gradient stages) are the fallback,
  not the default.
- **UI is small, calm, and native-looking.** Real-feeling system UI (notch
  pill, notification banner, dark task card with a live status line,
  Yes/No actions), NOT giant headline slabs. Let one element own the frame.
- **Type: quieter and more editorial.** No per-character rolls, selection
  sweeps, karaoke pills, or the "clean sans + coloured italic-serif accent word"
  combo (it reads as an AI template). No slogan headlines; prefer real UI labels
  and the speaker's own words. A proven caption: typewriter text in a dark
  monospace strip, typed as spoken. Captions = clean white bold
  humanist sans (Lato/Inter-like) with a soft shadow, no box, 2–3 words,
  centred mid-frame; only real speech is captioned. On-screen headlines are
  rare, short, and set with care (tracking, weight, optical size).
- **Motion is motivated.** Cut on action (press → listen → result → error →
  retry → accepted). Soft fades/small rises, gentle overshoot only on
  character pops, one real "camera" payoff (rack focus from UI to real object,
  a push into a laptop). No shockwaves, particle bursts, or bounce-everything.
- **Personality, not decoration.** If the brand has a mascot/character, it
  talks (bubbles, voice pill) and does things; it isn't a sticker.
- **Endings are quiet**: a black card with the mark → URL → one short CTA.
- **Sound**: natural human voice (hesitations kept), soft ambient bed, and small
  UI sounds, rather than a big drop.
- Keep a running list of lessons in `LEARNINGS.md` (next to this file). Read it
  before every new video, and append to it whenever a reference, feedback round,
  or finished video teaches something.

# Part 2 — Design the video (the build engine)

## Design system — original, premium, every time

Write a NEW design system in the composition file's header comment before
coding. It answers:
- **Stage** — the world (velvet dark? paper white? gradient dawn?) with ambient
  life (drifting particles, breathing glow, vignette). Static backgrounds read
  cheap.
- **Palette** — 2 brand colors + ink + dim ink from the real site CSS; one
  "hot" accent for hit moments.
- **Type treatment** — how headlines behave. Few words, set with editorial care
  (see Craft bar: no gimmick text effects by default).
- **Hero objects** — 2–3 drawn/animated objects from the audience's world (ring,
  rate ticker, parcel, waveform, search bar). **NEVER app-UI mockups or
  browser-window screenshots.** Line-drawn SVG (stroke-dash draw-in via
  `pathLength={100}`) reads premium. (For demos, redraw the real UI as clean
  original UI — still not a screenshot.)
- **Motion language** — pick 2–3 primitives, use them consistently.
- **Payoff effect** — what happens on the biggest hit; match the tone.

**Premium bar:** one idea per beat; generous negative space; hairline rules
over heavy boxes; nothing overlaps; any text to READ holds ≥2.5s; decorative
word-swaps may be faster. Kicker (small tracked mono caption) + big display
headline is a reliable premium layout.

**Cinematic-motion rules (non-negotiable — "it feels static" is the #1
rejection):**
- **Never pop-in-then-freeze.** Every scene gets continuous motion for its
  ENTIRE duration: a slow forward push (~6–11% scale over the scene) + gentle
  sinusoidal drift (±6–9px) at the scene-wrapper level. Err visible.
- **Stagger text vs object reveals.** Headline lands FIRST; the card/object
  swoops in ~14–16 frames later with a perspective tilt (rotateX ~9–14° → 0),
  large travel (150–280px), and an overshoot scale pop (spring damping ~13–15).
- **Cuts must "hit".** Zoom-through cross-dissolve: outgoing scales up
  (→~1.15–1.2×) + blurs + fades over ~9–11 overlapping frames while the next
  springs in from ~1.1–1.22× with blur→sharp.
- Sync the hardest cuts to musical hits (beatmap grid).
- **The payoff must READ within ~6 frames of the musical hit.** Give the payoff
  scene an instant full-screen flash/slam so it lands even mid-fade.

**Structure that works** (adapt, don't copy): cold-open hook or thesis →
problem/differentiator → 2–4 feature/outcome scenes → rapid-fire "and the
rest" → tension build → BIGGEST-HIT payoff → 3-verb triptych → logo/CTA end
card. A **cold-open bookend** (calm tease at 0s, full-fireworks on the drop) is
a proven upgrade — the calm version must drop the slam/particles.

**Reusable engineering pattern:** export the design primitives (Stage, scene
wrapper, text components, palette consts) from the composition so sequel cuts
import them unchanged. Decouple authoring from render with a temporal SCALE
(LOGICAL_FPS 30 → RENDER_FPS 60) and a spatial scale (author 1920×1080 →
render 3840×2160).

## Beats & music

Scene durations and internal beats are LOCKED to the track. Generate the grid:
```bash
node scripts/beatmap.mjs <track.mp3> [--duration 33.07] [--fps 30] [--no-window]
```
It detects onsets, scores by loudness × 1.5s follow-through, picks the best
window so the biggest hit lands at the payoff fraction, snaps a 10-slot grid to
real onsets, writes `<track>.beatmap.json` and prints BEATS durations + an
ffmpeg trim command. Use its `sceneDurations` as BEATS, `onsetFrames` for
internal beats. Proven ~33s@30fps shape: hook ~66f → build ~122f → 3 feature
beats ~110–135f → rapid-fire ~57f → tension ~140f → payoff ~96f (hit on first
frame) → triptych ~64f → end card ~92f.

**Window confirmation (mandatory for tracks longer than the video):** the
scorer's "best" window may be a section the user doesn't recognize. Cut the
chosen window + 1–2 alternates as short preview MP3s, give timestamps, let them
pick — or at minimum say which section you used.

**Getting music — must come from the user; never score with an unlicensed/
ripped track, never ship a "placeholder" score.** Preference: (1) user-supplied
licensed track → beatmap it; (2) Suno (manual ~1 min: give a copy-paste
instrumental prompt, steady BPM, clean intro, "one massive drop ~3/4 in"; paid
Suno = commercial rights); (3) a generation MCP tool if connected.

# Part 3 — Produce & deliver (the pipeline)

Run this for EVERY type. **Verify cheap before you spend big** is the through-line.

1. **Storyboard FIRST — approve before building.** Present in chat: (a) the
   design system in 3–4 lines, and (b) a 10-row storyboard table (slot ·
   seconds · scene concept · on-screen copy · beat moment). One
   approval/redline pass — the cheapest point to change direction.
2. **Start from `src/Harness.tsx`** (installed by setup.sh) — the generic
   scaffold: the 30→60fps SCALE harness, LayoutCtx/SceneCtx, `SceneFrame`
   (push+drift+zoom-through, with the blur-cost trap already handled), the
   Center/Kicker/Head/Sub primitives, `KaraokeCaptions`, and the root wiring
   that authors at 1920×1080 and scales ×2 to 4K. Import from it or copy it —
   do NOT re-derive this per project, it's where the paid-for bugs live.
   Replace `PALETTE` + `Stage` with the brand's own design system; that pair IS
   the look, and it should be genuinely new per video (anti-fingerprint).
   Write the composition in `~/promo-video-studio/src/<Brand><Type>.tsx`
   with the design system in the header. Register in `src/Root.tsx` at
   1920×1080@30fps **and ALWAYS also the 1080×1920 sibling** (`<Id>Mobile`,
   same component branching on `portrait = height > width`), even if 9:16
   wasn't requested. Typecheck: `npx tsc --noEmit`.
3. **Key stills BEFORE any video render** — render the make-or-break frames at
   half scale and READ them (hook, hero scene, payoff). Check contrast,
   legibility, hierarchy, accents against the background, nothing clipped/
   colliding:
   ```bash
   npx remotion still <CompId> out/check_<scene>.png --frame <F> --scale 0.5
   ```
   Never run multiple `remotion still` in parallel (npx bootstrap races) —
   loop sequentially.
4. **DRAFT render — OPTIONAL, and skip it when you're confident.** The stills in
   step 3 already catch typos/layout/colour for seconds of cost; a draft is a
   second full render the user waits on. Go straight to the final unless
   something is genuinely unproven (brand-new design system, unproven pacing, a
   risky effect) — and say why when you do fall back to one. When you do run it
   (~4× faster), verify exact frames (never `-ss` fast seek):
   ```bash
   npx remotion render <CompId> out/<slug>-draft.mp4 --scale 0.5 --crf 30
   scripts/frames.sh out/<slug>-draft.mp4 <outdir> 40 160 240 360 500 570 680 870 960 burst:<hitframe>
   ```
   READ every image: claims true, text readable, nothing clipped/colliding,
   gradients visible; the payoff peak lands within ~6 frames after the hit.
   Fix → re-render draft → re-verify only fixed frames.
5. **Final render at 4K** (only once verification passes), in the background:
   ```bash
   npx remotion render <CompId> out/<slug>.mp4 --log=info
   ```
   **Render cost:** avoid `backdrop-filter: blur()` on cards at 4K — the #1
   render-time killer (the compositor re-samples the backdrop per blurred
   element per frame). On light/white themes it's unneeded; prefer solid fills
   + crisp shadows. (This cut one render from ~1.25hr to minutes.)
6. **Voiceover — ElevenLabs (NOT HeyGen; HeyGen is legacy for this user).**
   Read `ELEVENLABS_API_KEY` from `.env` (gitignored; never echo it in chat or
   hardcode it into a script). Generate **per line** with
   `scripts/eleven-vo-ts.mjs <voice_id> <lines.json> <out_dir>` — the
   `/with-timestamps` endpoint, which also writes `<id>.words.json` word
   alignment you need for captions. Spell acronyms phonetically in the TEXT
   ("U-T-M", "C-P-C", "G-A four", brand "link U-T-M") — this is the difference
   between a clean read and a mangled one. **ASK which voice** and offer a
   preview before committing to captions/renders; a cloned voice can read
   marketing copy stiffly but suit a calm educational register.
   **Render SILENT and mux audio afterwards.** Never bake VO/music into the
   render: a VO change then costs a 2-minute remux (`-c:v copy`) instead of a
   multi-hour re-render. Burned-in captions are the ONE exception — those DO
   force a re-render, so get the voice approved first.
   **Fit the script to the scene grid, not the reverse.** Compute each scene's
   window, budget words at ~120–130 wpm (educational) or ~150–165 (short), and
   after generating compare each clip's length to its window. Regenerate only
   the lines that overflow. Give tight scenes a shorter lead-in (0.35s) and
   roomy ones 0.8–0.9s.
7. **Mux music (+VO) with sidechain ducking** (lands ~−12.5 dB; VO clear over
   music, drop still punches). Inputs 0=video, 1=music, 2=VO master:
   ```bash
   ffmpeg -y -i <video> -i <music> -i <vo> -filter_complex \
   "[2:a]volume=1.35,asplit=2[voc_mix][voc_sc];[1:a]volume=1.15[music];\
   [music][voc_sc]sidechaincompress=threshold=0.02:ratio=14:attack=4:release=350:makeup=1[ducked];\
   [ducked][voc_mix]amix=inputs=2:normalize=0,alimiter=limit=0.9,aresample=48000[aout]" \
   -map 0:v:0 -map "[aout]" -c:v copy -c:a aac -b:a 256k -shortest <out>
   ```
   Music-only variant: `[1:a]volume=1.25,alimiter=limit=0.95[aout]`.
   **Simpler alternative that works well for talk-led cuts** (explainer /
   tutorial), where music should sit quietly under a dominant voice:
   ```bash
   [1:a]volume=0.26[mus];[2:a]speechnorm=p=0.9:e=10[vo];\
   [vo][mus]amix=inputs=2:normalize=0,alimiter=limit=0.82,\
   apad,atrim=0:<DUR>,aresample=48000[aout]
   ```
   Lands ~−13.6 dB with the voice ~10 dB over the bed. **Never add a gain boost
   after the limiter** — a `volume=1.6dB` trim pushed peaks to +1.9 dBFS.
   **Fitting a music bed to an odd duration:** `atempo` beats looping. A track
   240s long onto a 250s video = `atempo=0.96` (exact, and a ≤5% tempo shift on
   an ambient bed is inaudible — it even suits a slower lesson). Add
   `afade` in/out at the ends.
8. **Audio verification (mandatory).** After ANY ffmpeg trim AND after the
   final mux: `ffmpeg -i <file> -af volumedetect -f null -`. Healthy mean ≈ −12
   to −20 dB; ≈ −91 dB = digital silence (put `-ss` BEFORE `-i`, never after).
   If VO is too quiet, ensure `asplit` feeds BOTH the sidechain trigger and the
   mix (a pad is consumed once). Check peaks with
   `-af astats | grep "Peak level"` — `volumedetect`'s max rounds to 0.0 dB and
   hides a real overshoot. Also verify VO **placement**, not just level: sample
   each scene window and each cut boundary (speech ≈ −21 dB inside a window,
   ≈ −91 dB in the gaps) so no line bleeds across a cut.
   **ffmpeg traps that cost real time:**
   - `apad` with no `-t`/`atrim` **never terminates** — it hung a mux until killed.
     Always bound it: `apad,atrim=0:<DUR>`.
   - `-shortest` silently trims the tail (lost 0.048s off a finished video).
   - `-ss` goes **before** `-i`; after `-i` it once silenced a whole music bed.
9. **Deliver the bundle proactively** — don't wait to be asked: copy the MP4(s)
   to the user's working directory; deliver both a **music+VO** and a
   **music-only** variant when VO is used; render the **9:16 vertical** *if the
   user asked for it in intake* (verify 2–3 portrait stills first — portrait
   layouts break silently); offer **burned-in captions** for social cuts; offer
   a **YouTube thumbnail** (a `Thumbnail.tsx`, 1280×720, `durationInFrames={1}`,
   2–3 concept variants using the exact design system; text huge enough to read
   at ~120px preview). Report a scene-by-scene table with timings, honesty
   judgment calls, and any licensing caveats.
   **Also ship, for anything going to YouTube:**
   - **An `.srt` sidecar** — and build it from the SCRIPT SENTENCES (proper case
     + punctuation, grouped ≤90 chars / ≤6s), *not* from the karaoke chunks
     (4-word ALL-CAPS fragments read terribly as a subtitle track). Timed by
     consuming the same word alignment. Burned-in captions are pixels YouTube
     cannot read; a real track adds search indexing, accessibility, and
     auto-translation.
   - **Chapter timestamps** derived from the real scene bounds. YouTube requires
     the first at 0:00, ≥3 total, and **every chapter ≥10s** — merge any scene
     shorter than that with its neighbour.
   - Titles / description / tags in one `-UPLOAD.md`.

# Universal rules & gotchas

## Quality rules (all types)
- **No flat pasted screenshots / browser-window mockups.** Either redraw the real
  UI as clean custom UI, OR use a real screen recording treated as a filmed
  object (grade, grain, drift, macro crop; see Craft bar). A raw, ungraded
  full-screen capture is never acceptable.
- **Something moves every frame** — never pop-in-then-freeze.
- **Pacing:** default unhurried + information-rich (readable headlines ≥2.5s,
  avg ~5s/scene); Social/Short is the one type that may run fast.
- **Look:** decide per video in intake. Real footage + filmed UI (Craft bar) is
  now the preferred direction; for purely illustrated pieces a light / crisp
  clean-white theme reads more premium than dark.

## Honesty rule
Every claim must be literally true of the product, OR explicitly authorized by
the user as aspirational (ask in intake, note it in the final report). On-screen
metrics must exist on the product's own site (citable), never invented. Example
prices/rates may be illustrative but plausible and current. When in doubt,
describe speed and visibility, not automation.

## Render safety — a clean log is NOT proof of a good file
These cost a full re-render. Treat them as mandatory.

- **GATE DELIVERY ON A DECODE CHECK.** Remotion logged `Encoded 3864/3864` with
  zero errors and wrote a plausible 50MB file that decoded to **114 frames**
  ("Invalid NAL unit size"). Before muxing AND before delivering, run:
  ```bash
  ffprobe -v error -count_frames -select_streams v:0 \
    -show_entries stream=nb_read_frames -of csv=p=0 <file>
  ```
  and compare to the expected count. Plain `nb_frames` (no `-count_frames`) also
  reads wrong on a corrupt file — only the decode count is trustworthy. Put this
  check inside the pipeline script so it refuses to deliver on mismatch.
- **A "killed"/"failed" background job may still be running.** The harness can
  kill the WRAPPER shell while `npx remotion render` and its
  chrome-headless-shell/ffmpeg children keep going as orphans. Before restarting
  anything, check whether the log and output file are still GROWING
  (`stat -c %s` twice, ~20s apart) and list live processes. Never restart a
  render that is actually still running.
- **But the killed wrapper never runs the steps AFTER the render** — the audio
  mux, the copy to the delivery dir, the done-marker. Any second job waiting on
  that marker is dead too. Recover with a resume script that waits on the render
  LOG for its completion string (`Encoded <N>/<N>`) instead of re-rendering, with
  a stall guard (bail if the log size hasn't changed in ~15 min).
- **Two renderers on one output path silently corrupts it** — that's what
  produced the 114-frame file: a killed job's wait-loop survived and raced the
  resume script, both writing the same `.mp4` and the same `> log`. When
  resuming or requeueing, ALWAYS write to FRESH filenames.
- **Never run two 4K renders concurrently** (CPU contention + OOM). Queue the
  second behind the first's marker file.
- **Concurrency:** 4K text-heavy comps crash browsers at `--concurrency=8`; 6 is
  stable. Remotion's ETA goes garbage (e.g. "65h") during a browser-restart
  stall — ignore it, the real pace resumes.
- **When cleaning up orphans, never kill bare `chrome`** — that's the user's real
  browser. Only `chrome-headless-shell` under `node_modules/.remotion/` is ours.

## Vertical (9:16) is a different layout, not a reframe
Portrait layouts break silently — always verify 2–3 portrait stills.
- **Type needs ~1.5–2× its landscape size.** Reusing landscape sizes produces a
  timid ribbon of content stranded in dead space. Concretely, on a 1080×1920
  logical canvas: hero param/label 68→96, body 36→52, big numeral 108→168, and
  scale shared components up explicitly (give them a `scale`/`size` prop rather
  than wrapping in a CSS `transform`, which doesn't affect layout flow).
- **Keep content roughly in y ≈ 330–1250 of 1920.** The top ~250 and bottom ~500
  are where the Shorts/Reels/TikTok UI (avatar, caption, action rail) overlays.
  Empty bands there are correct, not a mistake.
- **Watch the container width cap.** A centered content column capped at
  `LW*0.86` is only ~928px in portrait — a 124px headline overflowed and had to
  drop to 106px. Check the widest line before rendering.
- **Captions:** chunk to ~3 words in portrait (vs ~4 landscape), and mount the
  caption layer OUTSIDE the per-scene wrapper so scene blur/zoom transitions
  don't drag the pills around.
- **Don't cram to a round number.** Build the scene grid from the ACTUAL VO line
  durations; Shorts allows up to 3 minutes, so 64s at a readable pace beats a
  rushed 60.

## Hard-won gotchas (each cost a render)
- **`<Img>` / `<OffthreadVideo>` get a `max-width` cap from the studio's index.css.**
  Any oversized/cropped media (footage crops, face-bubble zooms) silently shrinks
  and shows parts you meant to crop out. Always set `maxWidth: "none",
  maxHeight: "none"` on media you position/scale yourself.
- **Real numbers must match the exact moment.** When reusing a screen recording,
  read the numbers on screen AT the line that references them (full-res frame);
  later frames of the same page can show a different workspace/date range.
- **`background-clip: text` needs typography on the SAME span as the gradient**
  (inherited styles clip to near-black in headless Chrome). Build one style
  object `{...typo, ...gradient}` on a single span.
- **`AbsoluteFill` lays out as a COLUMN** — set `flexDirection:"row"` for
  horizontal layouts.
- **Abs-positioned children of a 0×0 anchor** land relative to its corner, not
  center — give the container explicit w/h and use `calc(50% + Xpx)`.
- **Scrolling stacks need viewport masks bigger than you think**; collision-
  check orbiting/converging chips against center text.
- **Segmented bars clip labels** in segments <14% of total; render inline
  values only when wide enough.
- **Wide two-part uppercase headlines overflow 1920px** ≥70px — stack or drop
  to ≤62px. Keep chip copy ≤3 words, `whiteSpace:"nowrap"`.
- **Deterministic pseudo-randomness only** (`(i*137)%100` style) — no
  `Math.random()` in compositions.
- **Never run multiple `remotion still` in parallel**; render sequentially.
- **Shell cwd can drift/reset between calls** — use absolute paths.

## Moving this to another machine
The skill is self-contained: `SKILL.md` + `scripts/` is everything. To port it,
copy `~/.claude/skills/video-studio/` to the same path on the new machine and run
`bash ~/.claude/skills/video-studio/scripts/setup.sh`. That installs ffmpeg/node
if missing, scaffolds `~/promo-video-studio`, copies all helper scripts in, and
creates a gitignored `.env` stub.

What does NOT travel, and must be redone on the new machine:
- **API keys.** Never stored in the skill. Paste the ElevenLabs key into the new
  `~/promo-video-studio/.env`. Cloned-voice IDs live in the user's ElevenLabs
  account, so they work from any machine once the key is set.
- **Past compositions.** `src/*.tsx` from previous videos live in the studio, not
  the skill. Copy any you want to reuse as a design-system starting point.
- **Music/brand assets** in `public/`.
- **Memories.** Project/preference memories are per-machine; re-state standing
  preferences (pacing, light theme, which voice) or copy the memory dir over.

Keep the skill portable: if you write a helper script during a project, put the
GENERIC version in `skills/video-studio/scripts/` and add it to `setup.sh`'s copy
list. A script that only exists in the studio folder is a script that will be
missing next time.

## Refinement discipline (how videos actually land)
Videos are converged on, not nailed blind. Ship a strong draft fast, take the
user's reaction LITERALLY, and change **one dimension per round** — e.g.
too fast → more hold time within scenes (never resize scenes); too thin → add
info; too dark → recolor to a light theme; "doesn't feel like <audience>" →
swap the visual OBJECTS not just words; "change the template" → a genuinely new
system (recoloring doesn't count); "I love scene X" → protect it, reuse verbatim
in later cuts. Keep the music/scene grid untouched while iterating content.
Expect ~2–4 rounds. Always run the full intake batch on a NEW video request
(skip only what's already decided in-conversation).
